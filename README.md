# E22 双串口通信测试

在同一台电脑上打开 COM11 和 COM27，经过两只 E22 的无线链路，交替测试两个方向的通信。当前连接的型号为 **E22-400T22S**，两侧 M0/M1 均接 GND。也适用于其他提供 UART 透明传输接口的 E22 模块。

## 运行

在此目录打开 PowerShell：

```powershell
python -m pip install -r requirements.txt
python lora_test.py
```

默认 COM11 / COM27、9600 baud、8N1，每个方向发送 5 个数据包，单包接收超时 3 秒，每次发送完成后间隔 1 秒。

```powershell
# 保存本次测试日志
python lora_test.py --log test.log

# 修改串口、波特率、包数和等待时间
python lora_test.py --port-a COM11 --port-b COM27 --baud 9600 --count 10 --timeout 5

# 查看串口
python lora_test.py --list-ports
```

程序按 COM11 发 → COM27 收 → COM27 发 → COM11 收的顺序执行，避免半双工发送冲突。每包包含本次运行的随机标识、方向和序号，必须在**另一串口**收到完整匹配的数据才计为成功。读取支持串口分段到达；额外的前后字节不影响匹配。程序会清理接收缓冲区，请先关闭占用这两个串口的其他串口工具。

`PASS` 是单包通过；末尾 `SUMMARY A->B` 和 `SUMMARY B->A` 分别给出两侧成功包数、未通过比例及平均耗时。耗时包含电脑、USB、串口及无线传输延迟，不能直接当作纯空中延迟。退出码：0 全部通过，1 有包超时或内容不符，2 串口/日志错误，130 用户中止。Ctrl+C 可退出，串口自动关闭。

## 硬件和模块设置

- 若使用文档中的 E22-400TBL-01 / E15-UTL1 成套测试板，板内已有 USB-TTL 和模块串口连线，直接接 USB 及天线即可。若使用独立 USB-TTL 转接器，TXD 接对应 E22 的 RXD，RXD 接 E22 的 TXD，GND 共地。
- 除 M0/M1 外，还需安装电源选择跳线：将模块 **VCC 与 5V 短接**，与底板手册第 3 页示例一致。三针排针是 5V / VCC / 3.3V，中心是 VCC，只选择一侧。用户已确认本次两块板均选择 5V。
- 两侧处于正常传输模式。E22-400T22S 为 M0=0、M1=0；模式脚不要悬空。
- 两侧频段、信道、空中速率及相关网络参数应匹配；若启用了地址过滤、网络 ID 或加密，相关设置也需兼容。本示例要求两侧配置为透明传输。
- `--baud` 和 `--parity` 只设置电脑串口，必须与两只模块当前的 UART 设置一致。默认 9600 / 8N1 是初次测试假设，并非程序读取到的模块配置。
- 本示例只发送测试文本，不读取或修改模块寄存器。M0/M1 请在硬件上设定；程序未读取 AUX，使用固定间隔等待。E15-UTL1 原理图中 CH340 的 RTS/DTR/CTS/DSR 均未接到模块，因此程序不能通过它们控制 M0/M1 或读取 AUX。AUX 已引到排针和指示灯。

## 对照新增文档的结论

底板手册第 3 页「2.2. 模式 0 通讯」使用 9600、8 数据位、1 停止位、无校验，直接通过串口助手发送文本。当前测试程序与该流程一致，文档没有要求在每次透明传输前先发送 AT 指令、配置指令或地址头。若模块已被配置成定点传输，当前透明传输示例则不适用，需要先读取并核实实际配置。

对照模块手册后，已把默认测试包从 35 字节缩短为 24 字节。若模块分包长度设为最小的 32 字节，同时接收端启用每包 RSSI，原来的 35 字节可能分成两包并在中间插入 RSSI，导致完整字符串匹配失败。缩短数据包可避免常规测试中的这种情况；它不能解释此前接收始终为 0 字节的现象。

E15-UTL1 原理图的 CH340 和 PWR 灯分别由 USB 供电经稳压或直接供电，模块 VCC 另经 J3 跳线选择。因此 COM 口出现、PWR 灯亮不能单独证明模块已获得正常供电。发送时可观察 AUX 灯是否闪烁，作为模块是否有活动的线索；亮灭不能代替参数读取或电压测量。

已确认两侧 M0/M1 接地、两侧选择 5V。尚未确认模块实际信道、地址、网络 ID、空中速率及透明/定点传输设置。该底板手册主要描述接线，详细寄存器需参照 E22-400T22S 模块手册。

## 读取模块实际配置

`e22_read_config.py` 使用厂家 C1 只读命令，分别与两只模块进行本地串口通信。它只读寄存器 0x00–0x06 和可选产品信息 0x80–0x86，不写配置。参考[官方 E22-T 模块手册](https://www.cdebyte.com/pdf-down.aspx?id=4217)第 6 章。

1. 关闭其他串口程序。
2. 在文档所示底板上，保持电源选择为 5V、M0–GND 跳线插着，**拔下 M1–GND 跳线**。底板 R5/R6 提供 3.3V 上拉，使 M1=1、M0=0，进入配置模式。不要把 M1 接到 5V。
3. 等待模块完成模式切换，再运行：

```powershell
python e22_read_config.py --log config.log
```

配置模式固定使用 9600 / 8N1，不受正常工作时保存的 UART 参数影响。脚本输出地址、网络 ID、UART 参数、空中速率编码、信道、透明/定点模式等，以及两侧差异。厂家各代固件的部分低速编码含义不同，所以保留原始空中速率编码；出厂编码 2 对应 2.4 kbps。加密密钥为只写寄存器，读取结果不能判断两侧密钥是否相同。

读到有效 C1 响应，能确认该侧电脑到模块的 UART 查询链路可用，但仍不等于无线通信通过。读不到响应时，先检查实际 M0/M1 电平、模块 VCC 和板内连接。

读取结束后，将两块板的 **M1–GND 跳线重新插回**，恢复 M0=M1=0，再运行通信测试。切换模式不会重置保存的配置。

## 不通时排查

1. 串口无法打开：检查端口号、USB 连接及是否被其他程序占用。
2. `received 0 bytes`：先确认 M0/M1 模式、供电、TX/RX 接线，再核对两侧频段、信道、空中速率、地址和透明传输设置。
3. 收到乱码或内容不符：核对两侧 UART 波特率及校验位；程序会输出收到的字节和十六进制预览。
4. 偶尔超时：尝试 `--timeout 10 --interval 2`，检查天线、供电和干扰；这只能调整测试时序，不能修正无线参数不匹配。

E22 存在不同型号/固件，具体接线和参数应查对应官方手册。参考：[亿佰特 E22-400T22S 官方下载页](https://www.cdebyte.com/products/E22-400T22S/4)。

## 本机实测记录（2026-09-07）

- COM11、COM27 均识别为 CH340，均可正常打开。
- 9600 / 8N1，每方向 5 包、超时 3 秒：两个方向均 0/5，接收 0 字节，见 `test.log`。
- 9600 / 8N1，每方向 1 包、超时 10 秒：两个方向均 0/1，接收 0 字节，见 `test-long-timeout.log`。
- 补测 1200、2400、4800、19200、38400、57600、115200 / 8N1，每档每方向 1 包：均未收到数据，见 `test-baud-scan.log`。此扫描每次给两个电脑串口设置相同波特率，未覆盖两只模块使用不同波特率的组合。

这些结果说明在上述测试条件下未建立通信；仅凭串口能打开，不能确认 USB-TTL 到模块的接线和模块供电正常。还需核对模块实际参数及硬件连接。
